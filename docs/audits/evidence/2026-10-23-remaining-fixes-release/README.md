# Remaining fixes release evidence — October 23, 2026

The PostgreSQL ledger probe runs against session-temporary tables only, under an outer transaction that is rolled back, including its DDL. It verifies that the tables disappear afterwards. It does not read or mutate production event rows. The checked aggregate result is in `ledger-postgresql-probe.json`; the executable witness is `services/market-data/tests/_dark_pool_ledger_probe.py`.

The first image invocation failed before connecting because the test harness assumed repository path depth. The harness now supports the container layout; the unchanged application ledger passed via stdin in the release image. SQLite regression tests cover the same state transitions. Deployment status and suite totals are recorded in the linked release report.

Production verification outputs contain source hashes, image/build identities, health states, representative API results and counts. No credentials or tracking IDs are recorded. All 12 backend source/shared trees matched the isolated application release; all 15 containers were healthy; the frontend build ID matched the prepared image; `/`, `/stock/MU` and `/signal-tuning` returned HTTP 200. This is API/HTTP verification, not an interactive browser session.

Initial live ledger counts included 32 ambiguous IDs among 1,093 IDs (1,139 retained payload versions). Same-capture conflicting payloads are excluded from the baseline, including potentially metadata-only disagreements; the provider meaning of those conflicts has not been established. Zero cancellation tombstones had been observed in this sample; cancellation behavior is proven by the SQL regression probes rather than a live canceled print. Sampling was correctly degraded for MU because its response reached the bounded window limit.

Validation first found two fixtures still expecting cache v2 after the adapter moved to v3. Correcting them exposed a pre-existing test-order issue: the real-HTTP test class restored a third module instance, so route imports and patches disagreed. Restoring the original module in both import registries fixed it. The formerly failing reversed-order group passed 189 tests. These follow-ups change only tests, not the deployed application source.
