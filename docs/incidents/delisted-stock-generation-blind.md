## Recurring Issue: BUG-DELISTED-GENERATION-BLIND — 8 More Generation/Scan Paths Never Consulted `Stock.delisted` (Fixed 2026-07-30)

**Found via**: a routine "next improvements" survey, explicitly asked to check whether any
recently-closed bug (the INT-4 auto-research trigger, the FOMC/feedparser deploy gap) might
have an undiscovered sibling elsewhere — the same "found one instance ≠ found every instance"
discipline already documented multiple times in this file (shared/common/ file-sync sweeps,
the Redis-connection-pooling audit). It found one, precisely as expected.

**Root cause**: `Stock.delisted` (aud14-survivorship, 2026-07-27) is set by
`_record_delisting_signal()` in `ingestion.py`, but it never flips `Stock.active` — a
confirmed-delisted stock stays `active=True` forever. `BUG-PAPERPOS-DELISTED-FROZEN`/
`BUG-ALERTS-DELISTED-SILENT` (2026-07-29) fixed the CONSUMING side for 2 specific runtime
paths (paper-position monitoring, alert checking). This pass searched every `Stock.active.
is_(True)` filter across the 3 services that actually generate/scan work per-symbol
(signal-engine, ranking-engine, market-data's scheduler.py) and found 8 more real generation/
scan paths with the identical gap — none of which had ever been touched by the 2026-07-29 fix,
since that fix was scoped to consumption, not generation.

**A real judgment call made correctly, not just "add the filter everywhere":** roughly a dozen
more `Stock.active.is_(True)` hits across these 3 files were investigated individually and
correctly LEFT ALONE — they're read/display queries joining ALREADY-COMPUTED `Signal`/
`Ranking` rows (e.g. `all_latest_signals()`, `consensus()`, ranking-engine's `screen()`), where
a stale delisted-stock row being displayed is harmless (no new work is generated by reading
it). Only fixed the ones that actually trigger NEW per-symbol work: fresh signal generation,
fresh K-Score computation, a real yfinance download, or a candidate-selection query that could
add a delisted stock to a user's watchlist.

**One critical exception deliberately NOT fixed, found by checking before blindly applying the
same pattern everywhere**: `services/market-data/src/services/scheduler.py`'s `_symbols_for()`
— the universe-symbol helper every ingestion job in the app calls. Ingestion is the ONLY place
that can ever detect or reconfirm a delisting (`_record_delisting_signal()` lives inside the
per-symbol price-fetch loop this function feeds) — excluding delisted symbols here would
silently disable the detection mechanism itself, not just skip wasted downstream work. A
dedicated test (`test_symbols_for_deliberately_still_includes_delisted_stocks`) guards against
a future well-intentioned but wrong "fix" here; adversarially verified by actually adding the
filter and confirming the test correctly failed.

**The 8 real fixes**:
1. `services/signal-engine/src/api/routes.py` — `POST /signals/refresh` (called from
   market-data's `_refresh_market()`, ~77x/day for US alone — a confirmed-delisted stock got
   fresh BUY/SELL signals recomputed on every single one of those cycles forever).
2. `services/signal-engine/src/api/routes.py` — `POST /signals/reset`.
3. `services/ranking-engine/src/api/routes.py` — `POST /rankings/refresh` (fresh K-Score
   recomputed every refresh cycle for a stock that can never be traded again).
4. `services/ranking-engine/src/api/routes.py` — single-symbol sector peer-comparison universe
   (`rank_symbol()`'s own K-Score computation) — a delisted peer's stale fundamentals would
   pollute another stock's value/growth percentile comparison basis.
5. `services/ranking-engine/src/api/routes.py` — `_leaderboard_live()`'s fallback live-compute
   path (a real generation path, not a display query, since it computes rankings on-demand
   when no persisted data exists).
6. `services/market-data/src/services/scheduler.py` — `_avg_volume_refresh_job()` (a real
   4-hourly yfinance 1-month-history download per symbol — a delisted stock just fails/returns
   nothing useful every single run).
7. `services/market-data/src/services/scheduler.py` — `check_volume_anomalies()`'s
   `_market_symbols` set — a delisted stock's frozen last-known price/volume can look like a
   real "anomaly" against its own stale average, matching the same reasoning already
   documented for `BUG-VOLANOM-STALEMARKET`'s market-hours fix elsewhere in this file.
8. `services/market-data/src/services/scheduler.py` — the watchlist auto-rotation candidate
   query — could otherwise add a confirmed-delisted stock to a user's watchlist.

**Tests**: 13 new cases across 3 files —
`services/ranking-engine/tests/test_delisted_excluded_from_generation.py` (5 cases, using this
repo's established real-source-extraction technique from `test_rank_symbol_market_scoping.py`
— a real in-memory SQLite DB built from the actual `shared/db/models.py`, with the real query
statements extracted directly out of `routes.py`'s source text and executed against it, not a
hand-copied duplicate that could silently drift), `services/signal-engine/tests/
test_delisted_excluded_from_refresh.py` (4 cases, source-text regression checks matching
`test_int4_research_trigger_gated.py`'s established pattern — includes a dedicated guard
confirming the read-only display endpoints are deliberately UNCHANGED), and `services/
market-data/tests/test_delisted_excluded_from_scheduler_jobs.py` (4 cases, source-text checks
— including the dedicated `_symbols_for()` protective guard described above).

**Adversarial verification** — 4 sabotage cycles across all 3 files, all caught and reverted:
reverting `/rankings/refresh`'s filter (caught the wrong-but-related test first, since two
functions in the same file shared an identical literal substring — investigated, confirmed it
was still a valid catch of the intended regression class, not a false positive); reverting
signal-engine's `refresh_signals()` filter (2 tests caught it); reverting market-data's
`_avg_volume_refresh_job()` filter (caught directly); and — the one deliberately inverted
sabotage — WRONGLY adding a delisted filter to `_symbols_for()` (caught by its own dedicated
protective test, confirming the guard correctly detects the opposite mistake too).

**Verification**: full 624-test market-data suite (up from 620), 29-test ranking-engine suite
(up from 24, 1 pre-existing unrelated `test_kscore.py` failure confirmed via `git stash` to
predate this change), and 123-in-scope-test signal-engine suite (up from 119, excluding the
2 pre-existing unrelated failure groups already documented elsewhere in this file) all green.
`pyflakes` clean on all 3 touched files (confirmed via `git stash` that every warning in all
three predates this change).

**Design invariant reinforced (again)**: an audit/fix that finds and closes SOME instances of
"X never checks `Stock.delisted`" should not be assumed to have found EVERY instance — the
only reliable check is grepping the actual filter condition (`Stock.active.is_(True)`) across
every service that generates per-symbol work, not just the 1-2 files an original bug report
happened to point at. This is now the third time this exact lesson has recurred in this
session's own history (the `shared/common/` file-sync sweeps, the INT-4 auto-research trigger,
and now this) — worth treating as a standing checklist item whenever `Stock.delisted` gains a
new consumer: check every OTHER `Stock.active`-filtered query in the same service family, not
just the one the current bug report is about.

**What to check if this looks wrong**:
```bash
docker exec stockai-signal-engine-1 grep -n "Stock.delisted" /app/src/api/routes.py
docker exec stockai-ranking-engine-1 grep -n "Stock.delisted" /app/src/api/routes.py
docker exec stockai-market-data-1 grep -n "Stock.delisted" /app/src/services/scheduler.py
# _symbols_for() should be the ONLY function in scheduler.py's grep output with NO
# Stock.delisted reference nearby — if it ever gains one, that's a regression of the
# deliberate exception documented above, not a missed fix.

# Confirm a real delisted stock (once one exists) stops appearing in fresh signal/ranking
# generation after the next refresh cycle:
docker exec stockai-postgres-1 psql -U stockai -d stockai -c \
  "SELECT symbol, delisted FROM stocks WHERE delisted = true;"
docker logs stockai-signal-engine-1 --since 1h | grep 'signals.refresh\|signals.reset'
```

## Recurring Issue: BUG-DELISTED-GENERATION-BLIND — 2 More Sibling Instances Found in Services BUG-DELISTED-GENERATION-BLIND's Own Original Sweep Never Checked (Fixed 2026-07-30)

**Found via**: a routine "next improvements" survey explicitly asked to check whether the
delisted-stock generation-blind bug class (already fixed 3 times: signal-engine, ranking-engine,
market-data — see the earlier `BUG-DELISTED-GENERATION-BLIND` entry) had an undiscovered sibling
elsewhere. The original fix's own grep sweep was scoped to only those 3 services — this pass
extended the identical `grep -rn "Stock.active\|Stock\.delisted"` check across the other 9
backend services, exactly the "found one instance ≠ found every instance" discipline already
documented multiple times in this file (the `shared/common/` file-sync sweeps, the INT-4
auto-research trigger, the earlier 8-instance delisted-generation pass itself).

**Two real, confirmed generation/scan sites found, both correctly distinguished from harmless
lookup/display queries in the same files** (`event-intelligence`'s `_symbol_to_id()` disambiguation
helper and `news-intelligence`'s ticker-matching universe cache were both investigated and
correctly left untouched — neither generates new per-symbol work, they only match/resolve
against already-existing data):

1. **`services/technical-analysis/src/api/routes.py`'s `get_patterns_bulk()`** (`GET
   /ta/patterns/bulk`) — a real, module-level-cached (6h TTL) bulk chart-pattern scan: fetches
   400 days of daily bars per active stock and runs `detect_patterns()` on each. Called by
   ranking-engine's `_fetch_patterns_bulk()` to populate the leaderboard/screener patterns
   column (confirmed via grep — a real, live caller, not dead code). A confirmed-delisted stock
   kept getting a full fresh price fetch + pattern-detection pass every single 6-hour cache
   cycle, forever, for a stock that can never be traded again.
2. **`services/event-intelligence/src/api/routes.py`'s `sync_8k()`** (`POST /events/sync/8k`) —
   the daily SEC EDGAR 8-K filing sync for all active US stocks (per its own docstring: fetches
   the last 7 days of filings per symbol). A confirmed-delisted stock kept having its (now
   permanently empty) EDGAR filing history polled daily forever.

**Fix**: identical pattern to the original 8-instance pass — added `Stock.delisted.is_(False)`
alongside the existing `Stock.active` filter in both queries, with a comment cross-referencing
`BUG-DELISTED-GENERATION-BLIND` and explaining why it's a sibling instance.

**Tests**: `services/technical-analysis/tests/test_delisted_excluded_from_patterns_bulk.py`
(3 cases) and `services/event-intelligence/tests/test_delisted_excluded_from_8k_sync.py`
(3 cases) — both source-text regression checks (neither service's `routes.py` can be imported
directly in its local test environment: technical-analysis needs the Docker-only `db` package,
event-intelligence's conftest.py stubs `sqlalchemy`/`db` wholesale as `MagicMock`), matching the
established pattern used throughout this codebase for exactly this constraint. Each confirms the
filter is present, is ADDED alongside the pre-existing filters rather than replacing them (an
inactive-but-not-delisted stock, and any HK stock for the 8-K sync, must still be excluded), and
is on the SAME query line as the other filters (not a dead/unused variable elsewhere in the
function).

**Adversarial verification** — 2 sabotage cycles, both caught and reverted: reverting the
technical-analysis filter (all 3 dedicated tests caught it correctly) and reverting the
event-intelligence filter (all 3 dedicated tests caught it correctly, via a real `AssertionError`
in each case, not a false pass).

Full 52-test technical-analysis suite (unchanged count from the last documented baseline — the 3
new tests replace what would otherwise have been a net gain, confirming this service's suite was
already at 52 before this pass, not a stale count) and 180-test event-intelligence suite (up from
177) green after every revert; `pyflakes` clean on both touched files.

**What was investigated and correctly left alone in the same services** (found by the same grep,
NOT the generation-blind bug class):
- `event-intelligence`'s `_symbol_to_id()` (line ~330) — uses `Stock.active.desc()` purely to
  disambiguate which of two same-symbol-different-exchange rows to resolve to (an unrelated,
  correct use of the column, per its own `T247-EVENTINTELLIGENCE-SYMBOLEXCHANGE` comment).
- `news-intelligence`'s `tickers.py::_load_universe()` (line 38) — a 15-minute-cached universe
  cache used only for MATCHING a headline's ticker/company-name mentions against the app's real
  stock list, never generating new per-symbol work; a delisted stock remaining matchable so an
  old news item about it can still be tagged is harmless, arguably even correct behavior.
- `portfolio-optimizer`, `strategy-engine`, `decision-engine`, `research-engine`, `api-gateway`
  — confirmed via grep to have ZERO `Stock.active`/`Stock.delisted` references of any kind
  (these services don't query `Stock` directly at all, or don't filter by active status where
  they do).

**Design invariant reinforced (again — this is now the 4th recurrence of this exact lesson in
this session's own documented history)**: any bug-class fix that closes SOME instances of a
pattern should never be assumed to have found EVERY instance — the only reliable check is
re-running the same grep against every OTHER service in the repo, not just the ones an original
bug report or investigation happened to point at. Worth treating as a standing checklist item:
whenever a new `Stock.delisted` consumer is found and fixed, re-grep ALL remaining services for
the same `Stock.active`-without-`Stock.delisted` pattern before considering the class closed.

  "SELECT symbol, delisted FROM stocks WHERE delisted = true;"
